# Prometheus + Grafana — Interview Q&A

**Q: Why does Prometheus pull metrics instead of having applications push them?**
A: Pull gives Prometheus itself control over scrape timing and target health — if a target doesn't respond, Prometheus knows immediately (the scrape fails and `up` becomes `0` for that target), which is itself a useful signal. Pull also means application code doesn't need to know where the monitoring system lives or handle its own retry/backoff logic against a metrics endpoint — it just exposes `/metrics` and Prometheus decides when to read it. The tradeoff: pull doesn't fit short-lived batch jobs that finish before a scrape could happen, which is exactly why the Pushgateway exists as a deliberate exception, not a contradiction of the model.

**Q: When would you actually use the Pushgateway, and why not just use it everywhere for simplicity?**
A: The Pushgateway exists specifically for short-lived batch/cron jobs that complete and exit before Prometheus's next scheduled scrape would ever reach them — the job pushes its result metrics to the Pushgateway, which holds them until Prometheus scrapes the Pushgateway itself. Using it for regular long-running services defeats its purpose and actively causes problems: metrics pushed there persist indefinitely until explicitly deleted, so a service that pushes and then dies leaves stale, misleading metrics behind rather than correctly reporting `up == 0` the way a normal scrape target would.

**Q: What's the difference between the four Prometheus metric types, and why does it matter which one you pick?**
A: **Counter** only increases (or resets on restart) — used for totals like request count, always paired with `rate()` for anything meaningful. **Gauge** goes up and down — used for values with a current state, like memory usage or active connections. **Histogram** buckets observations (request duration, response size) into predefined ranges, enabling `histogram_quantile()` percentile calculations server-side. **Summary** calculates quantiles client-side at scrape time — cheaper for Prometheus to store but the quantiles can't be aggregated correctly across instances after the fact, which is the real reason Histogram is generally preferred over Summary for anything you might need to aggregate across a fleet.

**Q: What actually happens during a Prometheus scrape, step by step?**
A: Prometheus sends an HTTP GET to the target's `/metrics` endpoint on the interval defined in `scrape_configs` (commonly 15-30s). The target responds with plain-text metrics in Prometheus's exposition format. Prometheus parses that response, attaches the configured labels (job, instance, any relabeling), and appends the new samples to its local TSDB. If the scrape fails (timeout, connection refused, non-200 response), Prometheus records `up{job="...", instance="..."} == 0` for that target and the scrape simply contributes no new data points for that interval — this is why `up == 0` is usually the very first thing to check when a target's data looks like it stopped updating.

**Q: How does Alertmanager's routing tree actually decide who gets paged?**
A: Alertmanager receives firing alerts from Prometheus (which only evaluates alerting rules and fires — it does not itself send notifications) and matches each alert against a tree of `route` blocks, top to bottom, using label matchers (`team: payments`, `severity: critical`). The first matching route (or the most specific one, depending on `continue: true` settings) determines the receiver — a Slack channel, PagerDuty service, email list. On top of routing, Alertmanager also handles **grouping** (bundling related alerts — e.g. all instances of the same outage — into one notification instead of one per instance) and **inhibition** (suppressing a lower-severity alert like "high latency" when a related higher-severity alert like "service down" is already firing, since the first is a symptom of the second).

**Q: A Grafana dashboard shows "No data" for a panel — what's your actual diagnostic order?**
A: Check the panel's query directly in Prometheus's own UI first (Grafana adds a layer that can obscure whether the problem is the query or the datasource connection) — if the raw PromQL also returns nothing there, the problem is upstream of Grafana entirely (wrong metric name, label selector matching nothing, target not being scraped). If the same query *does* return data in Prometheus's UI but not in Grafana, check the panel's configured time range against when the data actually exists, and check the datasource configuration (URL, auth) for drift, especially after any Prometheus redeploy that changed its address.

**Q: Why use Grafana template variables instead of building a separate dashboard per environment/cluster?**
A: A `$environment` or `$cluster` dashboard variable, backed by a label-values query (`label_values(up, cluster)`), turns one dashboard definition into every environment's view via a dropdown — the query underneath each panel references `$cluster` instead of a hardcoded value. Maintaining one parameterized dashboard means a panel fix or new panel applies everywhere at once; maintaining N near-identical dashboards means every change has to be manually repeated N times and reliably drifts out of sync over time, which is the exact problem template variables exist to eliminate.

**Q: What's the actual scaling limit of a single Prometheus instance, and what do you do once you hit it?**
A: Prometheus is designed to run as a single binary with local disk storage — there's no built-in clustering for horizontal scale. The real limits are memory (proportional to active series count — this is why cardinality control matters so much) and local disk I/O for the TSDB. The standard scaling paths, roughly in order of complexity: functional sharding (split scrape targets across multiple Prometheus instances by team/service, each independently sized); `remote_write` to a long-term-storage backend (Thanos, Cortex, Mimir) that federates queries across shards and provides durable retention beyond local disk; or, for genuinely large multi-cluster estates, Thanos/Cortex/Mimir as the primary query layer with Prometheus instances reduced to being local scrapers feeding it.

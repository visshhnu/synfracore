# OpenShift — Interview Q&A

**Q: What are the real, practical differences between OpenShift and vanilla Kubernetes?**
A: OCP adds a full platform layer on top of Kubernetes: Routes (HAProxy-based, richer than Ingress) for external traffic, Security Context Constraints (stricter, more granular than PodSecurityPolicy) for pod security, a built-in image registry, an integrated web console and OAuth server, and the Operator Lifecycle Manager for managing operator installs/upgrades. Functionally it's still Kubernetes underneath — the `oc` CLI is a superset of `kubectl`, and standard Kubernetes manifests generally work — but the platform-level defaults and additional resources (Routes, SCCs, DeploymentConfig) are OCP-specific and worth knowing precisely, not assuming vanilla Kubernetes knowledge covers automatically.

**Q: A pod fails to start with "unable to validate against any security context constraint" — walk through your diagnosis.**
A: This means the pod's security requirements don't match any SCC bound to its ServiceAccount. Check what the pod is actually requesting (a specific UID, host network access, privileged mode) via its spec, then check what SCC its ServiceAccount currently has (`oc get scc`, `oc describe scc <name>`). The fix is almost always binding a more specific, appropriate SCC (like `anyuid` for a legacy app needing a specific non-root UID) — not reaching for `privileged`, which grants far more access than almost any application troubleshooting scenario actually needs, and defeats the security model SCCs exist to enforce.

**Q: Explain the three Route TLS modes and when you'd choose each.**
A: Edge terminates TLS at the router, plain HTTP to the pod — simplest, and the router retains request-inspection capability. Passthrough sends encrypted traffic all the way to the pod, with the router only routing on SNI, unable to inspect content. Re-encrypt terminates at the router then re-encrypts to the pod — end-to-end encryption plus router-level inspection, at the cost of an extra TLS handshake. Choose Edge as the default when the pod doesn't need to handle TLS itself; Passthrough when the application specifically needs to see the original certificate or the router genuinely shouldn't decrypt traffic; Re-encrypt when you need both end-to-end encryption and router-level routing/inspection logic.

**Q: What's the difference between CVO and MCO, and why does that distinction matter operationally?**
A: The Cluster Version Operator manages OCP's own platform version — upgrading the cluster's core components. The Machine Config Operator manages OS-level configuration on the actual nodes — kernel parameters, systemd units — via `MachineConfig` objects. The operational distinction matters because MCO changes trigger a real, disruptive rolling node drain-and-reboot across the affected pool, which needs to be scheduled deliberately (a maintenance window, one pool at a time), unlike most ordinary Kubernetes resource changes that apply without any node-level disruption at all.

**Q: Why would you set `installPlanApproval: Manual` on an operator subscription in production, given it means more manual work?**
A: `Automatic` approval means an operator upgrade published upstream (by the operator's maintainer, on their release schedule) applies to your cluster automatically — genuinely risky for anything production-critical, since it removes your ability to test an upgrade or choose your own timing before it takes effect. `Manual` requires explicit review and approval of each pending `InstallPlan`, trading some operational convenience for control over exactly when and whether an operator upgrade actually happens — a reasonable, common tradeoff for production specifically, even if `Automatic` remains fine for less critical environments.

**Q: How would you debug a deployment that's stuck, using `oc`-specific tooling beyond standard `kubectl` commands?**
A: `oc rollout status` confirms whether a deployment actually completed or is still progressing. `oc get events --sort-by=.lastTimestamp` surfaces recent cluster events chronologically, often naming the actual blocker directly (an SCC rejection, an image pull failure, insufficient resources). `oc debug` creates a copy of a problematic pod (or node) specifically for interactive troubleshooting, without disturbing the original — useful when you need a shell in an environment matching the failing pod's context but don't want to exec into (and potentially disrupt) the actual failing instance itself.

**Q: What are Infrastructure nodes, and why would a team deliberately use them instead of just running everything on Worker nodes?**
A: Infrastructure nodes run platform-level components (the router, the internal registry, monitoring stack) separately from application workloads on Worker nodes — the real, practical benefit in OCP specifically is licensing cost: Red Hat's OCP subscription model can treat Infrastructure-node-hosted platform components differently from Worker-node application workloads, making this a genuine cost-optimization pattern, not merely an architectural preference. It also provides workload isolation — a resource-hungry application on a Worker node doesn't compete with platform components for capacity on the same nodes.

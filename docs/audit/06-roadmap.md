## FIXED — Clerk ↔ Supabase Third-Party Auth integration was never configured
**Severity: Critical (production-impacting) — discovered 2026-07-08 during Phase 3.1 live verification, not part of the original 6-stage audit**

Every signed-in user's `ensureUserRecord()` call (`lib/supabase/ensureUser.ts`) was silently failing on **every** page load that calls it (`/dashboard`, `/onboarding`), for **every** user, the entire time — not a Phase 3.1 regression, not specific to one account. Symptom: a generic "We couldn't sync your profile just now" banner on `/dashboard`; the real error, only visible in server logs, was PostgREST returning `PGRST301: No suitable key was found to decode the JWT`.

**Root cause**: CLAUDE.md's own documented setup step ("Supabase: Authentication → Sign In / Providers → Add provider → Clerk → paste the Clerk domain") had never actually been completed in the Supabase dashboard. Supabase had no way to verify the signature of the JWTs Clerk was issuing, so it rejected all of them at the PostgREST layer — before RLS, before any query logic, before any application code ran at all. Since every `users` row is only ever created via this same upsert path, this also means **no user who signed in before this fix ever got a `users` row created**, and every one of `getProfile()`/`getProgressSummary()`/`getBookmarks()`/`getQuizSummary()`/etc. (`lib/supabase/queries.ts`) had been silently returning empty defaults for that same reason — not because those users had no data, but because the sync that would have created their row never succeeded.

**Fixed** (2026-07-08, dashboard configuration, not a code change): registered the Clerk domain `engaged-bobcat-8.clerk.accounts.dev` under Supabase → Authentication → Sign In / Providers → Third-Party Auth → Clerk. Confirmed fixed live: a real `users` row was created immediately on next `/dashboard` visit, sync banner gone, `/admin` renders correctly for the now-admin account.

**Why this wasn't caught by the original audit**: the audit reviewed code and RLS policy *text* against CLAUDE.md's documented architecture, correctly found the code matched the documented pattern, and had no way to check the *live* Supabase dashboard's actual provider configuration — this class of bug only surfaces by actually signing in and checking server logs, which is exactly what happened here.

Nothing to revert if this is ever undone — it's Supabase dashboard state, not a file in this repo.

## FIXED — `app/api/blog`'s Cloudflare KV access never actually worked (likes/comments likely never persisted)
**Severity: High (silent data-loss on a public-facing feature) — discovered 2026-07-08 during Phase 3.4 live verification, not part of the original 6-stage audit; the underlying bug predates this entire engagement**

`app/api/blog/route.ts` read its `BLOG_KV` Cloudflare KV binding as `(globalThis as any).BLOG_KV`. That binding was genuinely configured correctly in the Cloudflare Pages dashboard the whole time (confirmed via screenshot: Settings → Bindings → KV namespace → `BLOG_KV`) — but `@cloudflare/next-on-pages` compiles Next.js into the ES-modules Workers format, where bindings arrive via the fetch handler's `env` argument, not as JS globals (global-as-binding is only true of the legacy Service Worker Workers format). So `kv` was `undefined` on every single request in production, silently, the whole time — meaning the blog like/comment counters have most likely never actually persisted a single interaction, ever. Every "like" click and every comment submission appeared to succeed (the code's own `if (!kv) return { success: true, likes: 1, ... }` fallback is indistinguishable from a real response to a user), but nothing was ever saved.

**Confirmed live** (not just inferred): 21 rapid POST requests to `/api/blog` all returned the identical `{"success":true,"likes":1,"comments":[]}` — never incrementing. To rule out this being Cloudflare KV's own eventual-consistency staleness (a legitimate alternative explanation for "reads looking stale under rapid hits"), sent a second write to the same fresh test slug ~90 seconds later — well past KV's documented worst-case propagation window — and it *still* showed `likes:1`, confirming the binding was never reachable from the code at all, not merely slow to converge.

**Fixed** (2026-07-08, code change, part of Phase 3.4): added `getBlogKv()` to `lib/rateLimit.ts`, using `@cloudflare/next-on-pages`'s own documented `getOptionalRequestContext().env.BLOG_KV` API instead of the broken global reference. Both `app/api/blog/route.ts` and `app/api/subscribe/route.ts` (added in this same phase) now go through it.

**Why this wasn't caught by the original audit**: same category as the Clerk/Supabase finding above — the code *looked* internally consistent (checks for `kv` being falsy, degrades gracefully, matches its own comment "Falls back gracefully if KV not configured") and the Cloudflare dashboard binding was genuinely present, so nothing about either the code or the config in isolation looked wrong. The bug only exists in the gap between them — Next.js-on-Cloudflare's specific binding-access convention — and only surfaces by actually exercising the endpoint live and checking whether data really persists across requests, not by reading either side alone.

**Not yet confirmed**: this fix is committed but not yet deployed/live-verified as of this writing — needs a push + the same live re-test (rapid-fire + delayed-recheck) to confirm real persistence and that Phase 3.4's rate limiting now actually engages.

**Risk**: low technically (non-breaking to rendered output), but touches the single template serving the most traffic — verify against Phase 1.1's CI checks before shipping, and spot-check the same sample pages used in Stage 3 (Linux, Kubernetes, ICD-10-CM, AI fundamentals).

**Status (2026-07-13) — CLOSED, but this file had gone stale claiming otherwise for a while and needs to be checked against actual code, not assumed from this entry, if the question ever comes up again.** Two content templates share `SectionContent.tsx`, and they had drifted:

**Update (2026-07-08) — this finding's own premise ("not a known CVE") had gone stale by execution time, and the originally-recommended fix would have been actively dangerous.** By the time this was actually worked on, `next-on-pages`'s entire declared-compatible range (`<=15.5.2`) had become the *vulnerable* side of **CVE-2025-66478** ("React2Shell") — a CVSS 10.0, pre-authentication RCE in React Server Components, disclosed December 2025, affecting exactly this app's architecture (App Router + RSC), actively exploited in the wild. ### 3.7 Remove the `ClerkProvider` + Navbar Clerk-hook coupling that blocks all static rendering
*Discovered during Phase 2.2 (2026-07-08), named here as its own pre-scoped project — not a "performance" sub-task* — Every route in the app renders dynamically (confirmed: only 3 of 41 routes are static in the production build) because `<ClerkProvider>` sits in the root Server Component layout (`app/layout.tsx`) and resolves auth state via `headers()`/`cookies()` during SSR, which forces the entire tree dynamic under Next.js's rules. This is not fixable by a small per-page change: `components/layout/Navbar.tsx` — rendered on every single page — hard-depends on Clerk's `useAuth()` hook plus `<SignInButton>`/`<UserButton>`, all of which throw without a `<ClerkProvider>` ancestor. So no page can be made genuinely static without also solving Navbar's dependency.

**What the real fix requires** (scoped during Phase 2.2, not yet started):
1. Move every existing route under route groups — Next.js only allows one root-layout scheme per app, so introducing a second, `ClerkProvider`-free root layout (for genuinely static pages) means every current route needs to live in *some* group, not just the new one.
2. Build that second, `ClerkProvider`-free root layout with its own `<html>`/`<body>` for static-eligible pages (starting candidates: `/privacy`, `/terms`, `/about`, `/contact`).
3. Build a static-safe Navbar variant for that layout whose Sign In/Dashboard slot is its own small client island with a locally-scoped `<ClerkProvider>` — confirmed safe: Clerk supports nested providers sharing the same session, and the existing Navbar already gates that slot behind `isLoaded &&`, so there's no new loading-flash regression to design around.

**Interim mitigation already shipped** (Phase 2.2, commit `2805c85`): a `Cache-Control` header on `/privacy` and `/terms` set via `middleware.ts` (not `next.config.ts` — see that commit for why `next.config.ts`'s `headers()` silently no-ops on Cloudflare for any dynamically-rendered route). This cuts repeat-visit cost on two pages; it does **not** change their rendering mode and does nothing for the other 38+ dynamic routes.

**Update (2026-07-08) — attempted, made real progress, hit a genuine blocker, deliberately not merged.** Explored on a dedicated branch (`phase-3.7-static-marketing-pages`, committed but not merged — left in place so this work isn't lost). Two significant findings:

**1. The original diagnosis above was wrong, and the real fix is much smaller than scoped.** Confirmed via Clerk's own docs and a real build: regular `<ClerkProvider>` (no `dynamic` prop) does **not** force dynamic rendering by itself. The actual cause of every route being dynamic is `export const runtime = "edge"`, set once in the single root layout and inherited by every route beneath it — Next.js explicitly disables static generation for any page under an edge-runtime layout, unconditionally, regardless of ClerkProvider or anything else. Confirmed empirically: a route group with no edge-runtime export, using the **exact, unmodified** real `Navbar`/`ClerkProvider`/`Footer` (no static-safe Navbar variant, no nested-provider tricks), still builds as genuinely `○ Static`. So step 3 above (build a static-safe Navbar variant) turned out to be unnecessary — the entire fix is: route-group split (step 1) + a `ClerkProvider`-free-*looking* but actually just edge-runtime-free layout for static candidates (step 2, minus the Navbar rework).

**2. A real, confirmed blocker: `notFound()` calls triggered from *within* a matched route break under multiple root layouts.** Specifically Clerk's `auth.protect()` — which calls `notFound()` internally by default, and which every one of `/dashboard`, `/admin`, `/onboarding`, `/profile` relies on for its signed-out behavior — stops resolving to the app's custom `not-found.tsx` correctly once there's more than one root layout:
- With a single top-level `app/not-found.tsx` (today's structure): hitting `/dashboard` signed-out throws a hard `"not-found.tsx doesn't have a root layout"` error, 500 status.
- Giving each route group its own `not-found.tsx` (the fix Next's own docs recommend for multi-root-layout apps) removes the hard error — status goes back to 404 — but the actual rendered page silently falls back to Next.js's **generic, unbranded** 404 page instead of the app's real one.
- Confirmed via a temporary worktree of unmodified `main` that this is a genuine regression, not pre-existing behavior: the identical unauthenticated `/dashboard` request on `main` correctly shows the real custom 404 content today.
- Plain unmatched-URL 404s (no `notFound()`, no matched route at all) are **unaffected** either way — this is specific to the middleware-triggered `notFound()` path.

**Two candidate fixes identified, neither applied — both are product/security-posture calls, not unilateral engineering ones:**
- Change `auth.protect()` to redirect to `/sign-in` instead of calling `notFound()` for these routes. Fixes the bug cleanly, but reverses a deliberate existing decision to hide these pages' existence via 404 rather than reveal them via a redirect (see the "so a non-admin can't tell the page exists" comment on the admin page).
- Adopt Next's experimental `global-not-found.js` + `globalNotFound` flag (introduced 15.4.0, still marked experimental in Next's current docs) — untested whether it actually resolves the *middleware-triggered* case specifically (it's documented for the plain-unmatched-URL case), and stacks another experimental-feature risk onto a deploy pipeline that already caused one real incident this engagement (Sentry/`next-on-pages`).

**Decision: stopped here rather than push further into an increasingly deep Next.js edge case.** `main` is untouched. The branch (with the corrected diagnosis, the working `RootShell`/`AppChrome` shared-layout components, and the confirmed-static `/privacy`/`/terms` build) is preserved for whoever picks this up next — **start from the branch's findings, not from scratch, and resolve the `notFound()`/multi-root-layout question (likely via a product decision on the redirect-vs-hide question) before attempting to merge.**

**Do not re-derive this from scratch next time performance/SEO work comes up** — start from this item.

**Update (2026-07-09) — the real blocker turned out to be adapter-wide, not specific to this item's route-group approach. See "CONFIRMED — Static rendering is structurally blocked..." after 3.9 below: `@cloudflare/next-on-pages` can't correctly route the Server Action Clerk's SDK fires globally on sign-in, which blocks *any* static page on this adapter, not just the ones this item was trying to convert. 3.8 is now the prerequisite for this item, not a separate alternative to it.**

**Update (2026-07-10) — the redirect-vs-hide product question is resolved. `main` updated, live.** Decision: `/dashboard` and `/onboarding` now redirect a signed-out visitor to `/sign-in` explicitly (`auth.protect({ unauthenticatedUrl: ... })` in `middleware.ts`) — nothing sensitive about confirming these pages exist. `/admin` deliberately keeps its original, untouched `auth.protect()` call — no reason to confirm to a signed-out visitor that an admin panel exists at this URL. (Separately, `/admin`'s "hide from non-admins" behavior was always `admin/page.tsx`'s own `notFound()` against the Supabase `role` column, not a middleware concern — that stays exactly as it was.)

While tracing this, corrected an assumption baked into this item's earlier write-up: `auth.protect()` with no options does **not** uniformly call `notFound()` — traced directly in `@clerk/nextjs`'s source (`server/protect.js`): it already called `redirectToSignIn()` by default for normal page navigation, and only fell back to `notFound()` for non-page requests (Server Actions, non-HTML fetches). The explicit `unauthenticatedUrl` now makes `/dashboard`/`/onboarding`'s signed-out behavior deterministic regardless of request type, rather than relying on that implicit split.

**This resolves the specific risk this item's blocker was about — it does not unblock static rendering, and was never going to.** `/dashboard`, `/onboarding`, and `/admin` all still build as `ƒ Dynamic` (re-checked in the build output) — expected, since all three render genuinely personalized per-request data (auth state, Supabase queries) and were never static-rendering candidates themselves. What this fix actually buys: once the marketing-page route-group split (3.7's original goal — `/privacy`, `/terms`, `/about`, etc.) is attempted again, `/dashboard`/`/onboarding` living in the other, `ClerkProvider`-having root layout will no longer hit the `notFound()`-under-multi-root-layout bug this item originally found, since their signed-out path no longer depends on `notFound()` at all. The adapter-wide Server Action block recorded in "CONFIRMED — Static rendering is structurally blocked..." below is unaffected by this change and still requires 3.8.

### 3.8 Migrate off `@cloudflare/next-on-pages` to `@opennextjs/cloudflare`
*Discovered during Phase 3.5 (2026-07-08), named here as its own pre-scoped project — not something to attempt inside a routine dependency bump* — `@cloudflare/next-on-pages` is **Cloudflare's own deprecated adapter** (its install output says so directly: `Please use the OpenNext adapter instead: https://opennext.js.org/cloudflare`), and per 3.5 above, it's already latest (`1.13.16`) with no newer release in progress to track current Next.js versions. Its declared peer range for Next.js (`>=14.3.0 && <=15.5.2`) is now frozen in the past.

**Why this isn't a one-time fix**: 3.5 wasn't a fluke — it's the first instance of a structural, recurring conflict. Next.js ships security patches on its own schedule (this project already hit one CVSS-10.0 RCE within one audit cycle); a deprecated, unmaintained adapter's peer range does not move to track them. Every future Next.js security patch has some chance of landing outside whatever range `next-on-pages` was last tested against, forcing the exact same choice this finding faced: stay compliant with the adapter and risk running vulnerable code, or go out-of-range and carry an unacknowledged (if currently harmless) deploy-stability risk. Neither is sustainable as a repeating pattern for a platform meant to run 10-12+ years.

**Not urgent today** (the app deploys and runs fine on the current adapter), but should be picked up well before the next time a Next.js security patch forces this same choice again — reactively doing an adapter migration under CVE time pressure is a worse position than doing it deliberately now.

### 3.9 Invert the edge-runtime pattern: opt in per-route instead of inheriting it site-wide
*Discovered during Phase 3.8 (2026-07-08) as a byproduct of the OpenNext POC, named here as its own pre-scoped project — a likely-better alternative to 3.7's route-group approach, not a duplicate of it* — `export const runtime = "edge"` sits in the single root layout today and every route inherits it, which (per 3.7's corrected diagnosis) is the actual reason nearly every route is dynamic — not `ClerkProvider`. Confirmed via a real build: removing it entirely (with no other changes — no route groups, no second root layout) makes 20 of 42 routes go genuinely static, and the app still works correctly, including `/dashboard`/`/admin`'s signed-out 404 behavior (which 3.7's route-group approach broke).

**Proposed approach**: remove `runtime = "edge"` from the root layout, then explicitly re-add `export const runtime = "edge";` only to the routes that genuinely need per-request dynamic execution under `@cloudflare/next-on-pages` (the ones already showing `ƒ` for real data-dependent reasons — `/dashboard`, `/admin`, `/onboarding`, `/academies/[academy]/...`, `/api/*`, etc.) — inverting today's "opt out" pattern to an explicit "opt in" one.

**Why this is likely better than 3.7's route-group approach**: no multi-root-layout at all, so no `not-found.tsx`/`global-error.tsx` ambiguity to solve — 3.7's entire confirmed blocker doesn't exist here by construction. No Navbar changes needed (already established in 3.7's investigation). Much smaller diff than moving every route into groups.

**What's not yet verified**: this was tested with `plain next build` only, not through the actual `@cloudflare/next-on-pages` bundling step — needs the same branch + preview-deploy verification discipline as 3.5/3.7 before trusting it live. Also needs to double check every route currently relying on the *inherited* edge runtime doesn't have some non-obvious dependency on it beyond what a route-by-route audit would catch.

**Sequencing note**: probably supersedes 3.7 rather than sitting alongside it — worth deciding explicitly whether to attempt this instead of 3.7's route-group approach, not both.

## CONFIRMED — Static rendering is structurally blocked on `@cloudflare/next-on-pages` until 3.8 is done (2026-07-09)

Three independent attempts — 3.7 (route groups), 3.9 (edge-runtime opt-in), and 3.8's own POC — each separately tried to get *any* page statically generated while staying on the current adapter, and each hit a different symptom of the exact same underlying incompatibility. This time it was investigated to the actual root cause, confirmed directly in source and live, not just inferred from a symptom.

**The root cause**: Clerk's own SDK (`@clerk/nextjs`) uses a genuine Next.js Server Action internally — `invalidateCacheAction` in `node_modules/@clerk/nextjs/dist/esm/app-router/server-actions.js`:
```js
"use server";
async function invalidateCacheAction() {
  void (await cookies()).delete(`__clerk_invalidate_cache_cookie_${Date.now()}`);
}
```
`ClerkProvider.js` fires this from `window.__internal_onBeforeSetActive` on sign-in (and other "set active" events — sign-out is explicitly skipped on Next 15/16, which is why sign-in and sign-out symptoms differed slightly in testing). `@cloudflare/next-on-pages` has a confirmed, independently-documented limitation (real GitHub issues/discussions on the adapter's own repo, not speculation): **Server Actions return a 405 on any page that doesn't have `runtime = "edge"`.** Since `ClerkProvider` must be global — Navbar renders sign-in/sign-up on every page, by design, not a mistake — this Server Action can fire from wherever the user happens to be standing when they sign in. That means **every single page needs `runtime = "edge"` for Clerk to function correctly on this adapter, which is fundamentally incompatible with any page being statically generated at all** — not a scoping problem fixable with a more careful `ClerkProvider` placement.

**Confirmed live, not just in theory**: pushed a fix attempt (`phase-3.9-clerk-static-investigation`, implementing Clerk's own officially-documented `<ClerkProvider dynamic>` + `<Suspense>` pattern for the five auth-critical routes) to a real Cloudflare preview deploy. It made things *worse*, not better — sign-in hung indefinitely with no message, `/dashboard`/`/admin`/`/onboarding` stopped working, and the browser console showed exactly the `405` + "unexpected response" signature this documented limitation produces. Traced the mechanism directly in `node_modules/@clerk/nextjs`'s source afterward to confirm it precisely, rather than stopping at "the symptom matches."

**How this ties 3.7, 3.8, and 3.9 together** — each was solving the same goal and hit a different face of the same wall:
- **3.7** (route groups, multiple root layouts): blocked by `notFound()` ambiguity — a *routing* symptom of trying to isolate static pages from the rest of the app.
- **3.9** (edge-runtime opt-in, single root layout): looked correct through every check that didn't involve a real signed-in browser session — build output, curl, even the first live `curl`-based check — until actual sign-in/sign-out testing surfaced the Server Action 405. This is the one that got furthest before failing, precisely because the failure mode only manifests through real Clerk interaction, which none of the earlier verification steps exercised.
- **3.8** (`@opennextjs/cloudflare`): uses Node.js runtime via Cloudflare's `nodejs_compat` flag, not `next-on-pages`' per-route edge-Function compilation model — very likely does **not** have this specific Server-Actions-need-edge-runtime limitation, since the limitation is specific to how `next-on-pages` compiles routes, not to Next.js or Clerk themselves.

**This elevates 3.8 from "nice to eventually do, the durable fix for 3.5's recurring CVE-drift conflict" to the actual prerequisite for static rendering to ever work on this app at all.** It is no longer a parallel, optional improvement sitting alongside 3.7/3.9 — it is the *only* known path off this wall. Until 3.8 is actually completed (a real, working, live deploy — not just the local POC already attempted, which remains blocked on this Windows machine per its own entry above), static rendering for this app is not achievable on the current adapter. Full stop.

**Do not attempt any further static-page work on the current adapter** — no route groups, no edge-runtime removal, no variation or combination of either — until 3.8 is actually done. Every such attempt from this point forward is a known, confirmed dead end on `@cloudflare/next-on-pages`, not worth re-investigating from scratch. (If 3.8 itself is eventually completed and turns out to have some *comparable* limitation, that would need to be established freshly at that point — not assumed one way or the other from here.)

**Update (2026-07-10) — 4th symptom found, in production, and this one has a proven fix.** Live users going through onboarding hit "Couldn't save that" (error digest `360258681`) every time — 100% reproducible, not intermittent. Root cause: `auth()` inside `app/onboarding/actions.ts` (a genuine Next.js Server Action) threw `Clerk: auth() was called but Clerk can't detect usage of clerkMiddleware()`, even though the exact same `clerkMiddleware()` correctly protects that route on the page render (confirmed: signed-out visitors are still redirected/404'd correctly). This is the same family of problem as 3.7/3.8/3.9 — Clerk's SDK and this Cloudflare adapter disagree about how auth context reaches a Server Action — but a different manifestation: **missing auth context, not a 405.** Confirmed via [opennextjs-cloudflare#524](https://github.com/opennextjs/opennextjs-cloudflare/issues/524) that this reproduces on **both** `@cloudflare/next-on-pages` (what we're on) and `@opennextjs/cloudflare` (3.8's migration target) — so unlike the 405 case, this one is not even hypothetically fixed by completing 3.8.

**The fix that worked, live, confirmed twice** (commits `d83ff06`, `656dea9`, extracted into `lib/clerk/authFallback.ts`): when `auth()` comes back empty inside a Server Action, manually re-verify the session instead of trusting the broken context handoff. Since `clerkMiddleware()` already ran to let the request reach this route at all, the session cookie is present — only the AsyncLocalStorage propagation into the Server Action is broken. `clerkClient().authenticateRequest()` reads that cookie directly, bypassing the broken handoff entirely, and returns both the `userId` and the raw session token. The token matters as much as the userId: `createSupabaseServerClient()`'s `accessToken` callback (`lib/supabase/server.ts`) also calls `auth()` the same way, and was *also* silently failing — no JWT reached Postgres, so RLS-enabled tables (`user_domain_preferences`) rejected writes with `42501` even after the userId-only fix, while the `users` table (no RLS enabled) kept working and masked the problem for one extra round of live testing. Both call sites now go through the same `getAuthSafely()` helper.

**Why this is more than a one-off fix**: this is a working, confirmed-in-production pattern for keeping Clerk auth functional inside a Server Action on this exact adapter stack, without waiting on 3.8. If 3.8 is ever completed and this same context-loss problem turns out to affect OpenNext too (plausible — issue #524 above is filed against OpenNext, not `next-on-pages`), this fallback pattern is the first thing to try there as well, not something to re-derive from scratch. Scope check done 2026-07-10: `app/onboarding/actions.ts` was, and remains, the *only* `"use server"` Server Action anywhere in this codebase — dashboard, admin, and `/api/ai` all call `auth()`/`currentUser()` only from Server Components or a plain Route Handler (normal request paths, unaffected by this specific bug), so no other call site needed the fallback today. Whoever adds the next Server Action that needs `auth()` should use `getAuthSafely()` from the start rather than the raw import.

**Update (2026-07-11) — 5th symptom found, immediately after resolving 3.7's redirect-vs-hide decision, and it turned out to predate this entire engagement.** After the split policy above shipped, live testing of `/admin` (which deliberately kept its original, unmodified `auth.protect()` call — no options) showed a signed-out visit briefly flash the real 404, then fall through to the homepage. Confirmed via two separate live tests — a cold fresh incognito visit with no prior sign-in, and right after clicking sign-out — that this is **not** the already-documented `afterSignOutUrl`-missing quirk (Phase 4): that one only fires on an actual sign-out event, but the cold-fresh-visit case reproduced it with none.

**Root cause, traced directly in `@clerk/nextjs`'s source**: `auth.protect()`'s default signed-out behavior calls `notFound()` from *middleware*, which Clerk implements internally as `NextResponse.rewrite(new URL('/clerk_${Date.now()}', ...))` — a rewrite to a deliberately nonexistent path, relying on Next.js's normal "no matching route → render the app's custom `not-found.tsx`" behavior. **`@cloudflare/next-on-pages` does not correctly handle this pattern** — confirmed against three independent, already-filed upstream issues ([#177](https://github.com/cloudflare/next-on-pages/issues/177), [#283](https://github.com/cloudflare/next-on-pages/issues/283), [#546](https://github.com/cloudflare/next-on-pages/issues/546)): a middleware rewrite to a path that isn't a real route falls through to default/home-page handling on this adapter, instead of Vercel/local's correct behavior. This is the exact symptom observed.

**This means `/admin`'s "hide via 404" design intent likely never worked reliably in production on this adapter, predating this entire engagement** — confirmed NOT a regression from the redirect-vs-hide fix above via a direct `git diff` (the `auth.protect()` call for `/admin` was byte-identical before and after that commit; `admin/page.tsx` had zero changes in that window either).

**The fix that worked, live, confirmed** (commit `49aa8f7`): stop relying on middleware's `notFound()`-via-fake-rewrite mechanism for `/admin` entirely. Removed `/admin` from middleware's `isProtectedRoute` matcher, so it no longer calls `auth.protect()` at all — `clerkMiddleware()` itself still runs for every request regardless (it's not scoped to `isProtectedRoute`), so Clerk's auth context is still correctly established. `admin/page.tsx`'s own Server Component already called `notFound()` directly for the signed-in-but-not-admin role check (against the Supabase `role` column) — it now covers the signed-out case the same way, since `ensureUserRecord()` returns a null profile when `currentUser()` resolves to null. A native, officially-supported use of `notFound()` from within a Server Component render doesn't go through the broken middleware rewrite path, and correctly renders a stable 404. Live-verified: fresh incognito visit to `/admin` now shows a stable "Page Not Found" page, no flash, no fall-through — and signed-in admin access is unaffected.

**Why this is more than a one-off fix**: "move the auth check out of middleware and into the page component's own Server Component render" is now a second working, confirmed-in-production pattern for this adapter (alongside `getAuthSafely()`'s manual cookie fallback for Server Actions) — anywhere a route needs `notFound()`-on-signed-out semantics specifically (not a redirect), doing it at the page level sidesteps this adapter bug entirely, since it never invokes middleware's rewrite trick. This is directly relevant to how 3.8's eventual migration should be scoped: if `@opennextjs/cloudflare` handles `NextResponse.rewrite()` to a nonexistent path correctly (unconfirmed — 3.8's build is still blocked, see above), middleware-level `auth.protect()` defaults could be restored there; if not, this page-level pattern is the one to reach for again rather than re-deriving it.

**`/profile` still uses the original, unmodified `auth.protect()` default and was explicitly left out of this fix's scope.** Live-tested (2026-07-11) and confirmed **not** affected by this bug — it redirects cleanly to `/sign-in` with `redirect_url` set, no flash, no 404. This is consistent with Clerk's own source: `auth.protect()`'s default only falls back to the broken `notFound()`-rewrite path for non-page requests (Server Actions, non-HTML fetches) — a genuine full-page browser navigation to `/profile` hits `redirectToSignIn()` instead, which doesn't go through the broken rewrite mechanism at all. (Why `/admin` took the `notFound()` path instead of the same `redirectToSignIn()` default that `/profile` gets isn't fully resolved — moot now, since `/admin` no longer goes through middleware's `auth.protect()` at all — but if `/profile` (or any future route) is ever seen taking the `notFound()` branch for a real browser navigation, that would be worth understanding rather than assuming it can't happen.)

**Update (2026-07-13) — 6th symptom found, a genuinely new failure mode distinct from all three mechanisms above (405/edge-runtime, missing auth-context, `notFound()`-rewrite) — this one lets dispatch succeed and still 404s from inside Next.js's own Server Action verification.**

- Not the missing-auth-context issue: `app/question-bank/actions.ts` already used `getAuthSafely()` (the confirmed fix for that bug) from the start.
- Not the `/admin` `notFound()`-rewrite issue: nothing in this flow calls `auth.protect()` or `notFound()`.

**Root cause, confirmed via live runtime instrumentation, not inference or static file comparison** — after exhausting static analysis (manifest content, build IDs, compiled bundle contents, deployed artifact vs. source all confirmed byte-correct and consistent, none of which explained the symptom), temporarily patched the compiled `_worker.js` router with targeted `console.log` calls at the Worker entrypoint, the header-based Server Action dispatch matcher, and the final response-resolution function, deployed directly via `wrangler pages deploy` (bypassing a full rebuild to preserve the patch), and captured real request traces via `wrangler pages deployment tail`. Result: next-on-pages' own routing/dispatch layer works **correctly** — its generated header-matching rule for the exact `next-action` ID the browser sent returns `MATCH=true`, correctly identifying and routing to `startAttemptAction`. Application code (`startAttemptAction`'s own body) never executes at all — zero exceptions, zero `console.error` output, confirmed across two separate live-tail sessions. This means Next.js's own Server Action manifest/encryption-key verification, running *inside* the correctly-dispatched compiled function, independently decides the action ID doesn't resolve and produces its own internal not-found response — a failure one layer deeper than next-on-pages' routing, and downstream of where `getAuthSafely()` operates, so that fix has nothing to act on here.

**Adjacent causes investigated and ruled out along the way** (each real to check, none was the actual cause): `SUPABASE_SERVICE_ROLE_KEY` missing then correctly added, both locally and as a Cloudflare Secret; a missing table-level `GRANT` for `service_role` on the question-bank tables (a real, separate bug, fixed in `docs/question-bank-schema.sql`); a middleware route-matcher syntax bug, raw regex used where path-to-regexp syntax was required (a real, separate bug, fixed in `middleware.ts`); `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY` confirmed correctly baked into the build and byte-identical across the deployed artifact, the live-served HTML, and the browser's actual sent header; browser/CDN caching ruled out via fresh incognito sessions and a different browser.

**The fix**: convert `startAttemptAction`, `saveAnswerAction`, and `submitAttemptAction` from native Server Actions (`<form action={...}>` / direct client invocation) to plain Route Handlers invoked via client-side `fetch()`. A Route Handler is an ordinary HTTP endpoint — it never goes through Next.js's Server-Action-ID manifest/encryption dispatch mechanism at all, so this failure mode becomes structurally inapplicable, the same pattern already used to sidestep the `/admin` `notFound()`-rewrite bug (move off the broken mechanism entirely rather than patch it).

**Why this reinforces, not undermines, 3.8's priority**: this is the *fourth* distinct Server-Action-related failure mode found on this adapter across two features (Clerk's SDK, and now question-bank), each invisible locally and only found through live production testing. The pattern is now well-established enough to treat as a standing risk for *any* future Server Action on this adapter, not a one-off: **default to a Route Handler + client `fetch()` for any new mutation on this adapter, and only reach for a native Server Action if there's a specific reason to (e.g., progressive-enhancement `<form>` behavior actually matters) — and even then, budget time for live-only verification before considering it done, since local testing has now been wrong 4 times in a row for this exact class of bug.**

`index.func.js`: 30/30 entries malformed, 0 correct. `academies.func.js`: 0/30 malformed, 15/15 correct. Not a partial or racy corruption — the entire manifest for this one route's compiled bundle is in the wrong shape, while every other tested route's manifest is entirely correct.

**Complexity-threshold theory tested and falsified.** Homepage imports meaningfully more client-boundary-adjacent modules than `academies/page.tsx` (1 local `"use client"` component vs. 0, 11 distinct `lucide-react` icons vs. 1), which looked like a plausible trigger. Two diagnostic rebuilds (build-only, not deployed) disproved this:
1. Dynamically importing the one local client component (`NewsletterSignup` via `next/dynamic`, no `ssr:false` — not permitted in a Server Component) — manifest unchanged: still 30 malformed / 0 correct.
2. Reducing `app/page.tsx` to a one-line stub with zero imports beyond the shared root layout — manifest **still** 30 malformed / 0 correct, byte-identical counts to the full page.

The malformed-entry count does not change regardless of the route's own content or complexity. This rules out a page-content threshold entirely and points to something tied to the `/` route's identity or position in the route tree (most plausibly its role as the app's root/index route) rather than anything rendered on it — **correct as a diagnostic conclusion, but the "30 malformed / 0 correct" framing above was measuring the wrong section of the manifest, corrected below.**

**Actual root cause, confirmed by tracing the defect back through every generated artifact to its first producer:** the `(ssr)/./path` entries quoted above are from `edgeSSRModuleMapping` — a legitimately different sub-object from the one the browser runtime actually queries, `clientModules`. Re-examining `clientModules` specifically (not `edgeSSRModuleMapping`) found the real defect: `index.func.js`'s `clientModules` map had 54 of its keys written as **Windows-style absolute paths** (`d:\synfracore\node_modules\...`, backslash-separated) instead of the POSIX paths (`/mnt/d/synfracore/node_modules/...`) every working route's manifest used, `academies.func.js` included (77/77 keys POSIX, 0 Windows-style). Since the Worker executes in a POSIX environment, every runtime lookup against a Windows-keyed manifest entry fails to match — precisely reproducing "Could not find the module in the React Client Manifest" for every client reference on the route, framework internals included.

Traced backward through every generated file (`.next/cache`, `.next/server/app/page_client-reference-manifest.js`, `.vercel/output/functions/index.func/index.js`, `.vercel/output/static/_worker.js/__next-on-pages-dist__/functions/index.func.js`) — all four had identical counts (54/54/54/54), and the earliest-producing file, `.next/server/app/page_client-reference-manifest.js`, is **raw, unprocessed `next build` output** written before `next-on-pages` runs at all. This conclusively rules out `next-on-pages` and Cloudflare as the source: **Next.js's own webpack/RSC compiler emitted Windows-style paths for the root route's client-reference-manifest specifically, while resolving every nested route's manifest correctly with POSIX paths, in the same build.** The distinguishing factor was the filesystem, not the route: every build all night had been run via `cd /mnt/d/synfracore && npm run pages:build` — WSL, but against the Windows-mounted drive path, not WSL's own native filesystem.

**Fix, confirmed empirically**: copy the project to WSL's native filesystem (`rsync` to e.g. `~/synfracore-build`, ext4 — never `/mnt/d/synfracore`) and build there. Rebuilding from the native path produced a `clientModules` map with **0 Windows-style keys, all POSIX**, and a correctly populated `ssrModuleMapping` (previously empty for this route), matching the working routes' manifest shape exactly. Deployed and confirmed live: homepage 200 with real content, Academies dropdown interactive, question-bank Start flow working signed-in, sign-in/sign-out round-trip working, `/dashboard`/`/academies`/`/roadmaps` all 200.

**Distinct from symptom 6 (question-bank Server Action 404) in mechanism, root cause, and fix — do not conflate the two.** Symptom 6 was Next.js's Server Action ID/encryption manifest failing to resolve inside an otherwise-correctly-dispatched function, a genuine `@cloudflare/next-on-pages` limitation with no adapter-side fix, worked around by moving off Server Actions entirely (Route Handlers + `fetch()`). Symptom 7 was React Server Components' client-reference-manifest containing wrong-OS-format paths, a Next.js compiler defect triggered by building from a Windows-mounted WSL drive rather than a native Linux filesystem — not an adapter limitation at all, and fully fixed by changing *where* the build runs, no application code changed. Both happened the same night, both share the "invisible locally, only manifests on live Cloudflare Workers" signature, both are filed under this adapter-family section — but they are different bugs with different fixes. Symptom 6's Route-Handler fix **does not apply to symptom 7**, and symptom 7's native-filesystem fix **does not apply to symptom 6** (that one is a genuine dispatch-mechanism defect, not a path-encoding issue).

**Standing requirement going forward, not just for this incident**: build exclusively from a native WSL/Linux filesystem path for every future deploy — `/mnt/d/synfracore` (or any Windows-mounted drive path) must never be used for the `next build` / `pages:build` step again. See the pre-deploy checklist in `CLAUDE.md` for the full, mandatory verification sequence this incident also prompted.

**Update (2026-07-14) — 8th symptom found, UNRESOLVED, deferred to next session. Not urgent: the core question-bank Start flow works correctly once a user is already signed in (confirmed live, both before and after this was found) — this is specifically about the sign-in *redirect* handoff when a signed-out user clicks Start.**

User reported perceived slowness signing in/out specifically on `/question-bank/[paperSlug]` pages (first raised after the parallelization fix below, which did not resolve it — confirmed the fix addressed the page's own data-fetching latency, not this). Investigation moved from "slow" to "actually broken" once live evidence was gathered. Two pieces of concrete evidence collected, both from the browser's own Network tab during a real signed-out → Start → sign-in attempt on `/question-bank/bchhc-practice-1` (data the assistant cannot generate itself — no live browser access this session; both pieces came directly from the user):

1. A `POST` to `https://synfracore.com/sign-in?redirect_url=%2Fquestion-bank%2Fbchhc-practice-1` — **the sign-in *page* itself, not a Clerk API endpoint** — returns **404**. `/sign-in` is a plain Next.js page (`app/sign-in/[[...sign-in]]/page.tsx`, a Server Component rendering `<SignIn />`), which normally only handles `GET`; a `POST` landing on it 404ing rather than the more standard `405 Method Not Allowed` is itself suspicious and may be another next-on-pages routing-layer quirk (see symptoms 6 and 7's own history of this adapter mishandling non-standard request shapes), or may be an artifact of how Clerk's client SDK is issuing this request in the first place.
2. A genuine `400` from Clerk's own API — a request to `sign_ins?__clerk_api_version=...` — occurring around the same redirect, alongside the `<SignIn />` UI itself showing a **"You're already signed in"** error message. This is the signature of a client/server auth-state conflict: the server-side check that triggered the redirect to `/sign-in` (see below) decided the user was signed out, while Clerk's client-side SDK still considered the session valid by the time the sign-in page loaded.

Both response bodies were empty/uncopyable in the user's DevTools session (Preview and Response tabs showed nothing extractable) — only method, URL, and status were confirmed. **Getting the actual response body of the 400 (Clerk's own `code`/`message` fields) is the single most useful next step** — it would distinguish the token-rotation-race theory below from an unrelated Clerk configuration issue.

**What's structurally unique to this flow, confirmed from code** (see `app/api/question-bank/start/route.ts`):
- This is the **only** redirect-to-sign-in path in the codebase that appends a `redirect_url` param (`/sign-in?redirect_url=${encodeURIComponent(...)}`). Middleware's own auth redirects (`/dashboard`, `/onboarding`, `/question-bank/:paperSlug/attempt(.*)`) all use a bare `unauthenticatedUrl: "/sign-in"` with no `redirect_url` — see `middleware.ts` line 117. `<SignIn />` itself has zero props (`app/sign-in/[[...sign-in]]/page.tsx`), so it relies entirely on reading `redirect_url` from the URL, Clerk's own documented convention — this part is not misconfigured, but it IS the only place in the app exercising this code path at all.
- The auth check that decides to issue this redirect is `getAuthSafely()` (`lib/clerk/authFallback.ts`) — a fresh, independent server-side re-verification (`auth()`, falling back to `clerkClient().authenticateRequest()` on a manually-constructed `Request` if the primary path fails), triggered fresh on every `POST /api/question-bank/start` click. No other `getAuthSafely()` call site (onboarding, save-answer, submit, the attempt/results pages) redirects to sign-in in response to its result the way this one does.
- One independent code smell found along the way, not yet confirmed as the cause but worth fixing regardless: `getAuthSafely()`'s manual fallback path constructs its verification `Request` with a **hardcoded URL** (`new Request("https://synfracore.com/", {...})`) instead of the actual incoming request's URL. Clerk's `authenticateRequest()` primarily keys off the cookie header, so this may be harmless — but it's a landmine sitting in a shared helper used by 8 call sites, worth auditing properly rather than assuming.

**Leading theory, not yet confirmed**: a token-rotation race. Clerk's client SDK periodically rotates its short-lived session token in the background. If `POST /api/question-bank/start` fires (carrying whatever cookie exists at that instant) in the small window where the server-side token is mid-rotation, `getAuthSafely()`'s fresh re-verification can read a just-expired/mid-refresh token and conclude "signed out" — triggering the `/sign-in?redirect_url=...` redirect — while the browser's own in-memory Clerk state is still confidently signed in by the time `/sign-in` actually loads, producing the "already signed in" conflict and the `sign_ins` API's 400 rejection. This would explain evidence #2 directly. It does not, on its own, explain evidence #1 (the `POST` to the sign-in *page* itself 404ing) — that may be a separate, adapter-level routing quirk consistent with symptoms 6/7's established pattern (`@cloudflare/next-on-pages` mishandling non-`GET` requests against a plain page route), or may turn out to be related once the actual request initiator (Clerk's own client JS, not application code) is identified.

**Not urgent, deferred to next session**: the underlying Start flow works correctly for an already-signed-in user (re-confirmed live multiple times tonight, including after the `Promise.all` fix below). This symptom is specifically about the edge case of a signed-out user hitting the sign-in handoff at exactly the wrong moment during a background token refresh — a real bug, but not blocking the feature's core path. **Next session, prioritize getting the actual response body of both the `sign_ins` 400 and the `/sign-in` POST 404** (`curl`/server-side reproduction has already been tried and failed to reproduce either — see this entry's investigation trail — so this needs a real, instrumented browser session, not another structural code comparison).
